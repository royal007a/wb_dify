# 四份 PDF 阅读总结及对 Hify 的落地

## 材料范围

四份材料是《Claude Code 企业级全链路开发实战》的连续四讲：产品定义、应用架构与代码组织、部署/性能/数据设计、CLAUDE.md/Skills/工程规范。PDF 共 25 页，均为网页截图，无文本层；本轮通过逐页渲染、OCR 和页面视觉核对完成阅读。

## 1. 产品定义：第一行代码前先砍范围

核心方法不是罗列需求，而是先看标杆全貌，再用“三问裁剪法”做取舍：没有它产品是否成立、做到什么程度够用、能否一句话讲清产品。课程把 Hify 约束为一人开发、20-50 人内部使用，因此保留模型、Agent、对话、工具和管理台；RAG/Workflow 降级；可视化、多租户、插件市场、计费等砍掉。

**融入设计**：`SPEC.md` 把能力分成 P0、P1、非目标，并为每项给出可测成功指标。Dify 只提供能力全景，不决定 Hify 的范围。

## 2. 架构上：模块化单体不是“所有代码堆一起”

课程在 package 分层、Maven 多模块、微服务之间选择模块化单体：部署仍是一个应用，但 provider、agent、chat、tool/MCP、knowledge、workflow 在代码层隔离，依赖单向，跨模块只通过 Service 接口。Controller、Service、Mapper、Entity、DTO 有明确职责。对慢且不稳定的 LLM 外调，要同时设计隔离、熔断、超时和分类重试。

**融入设计**：Hify 已建立 Maven 多模块结构；跨模块依赖和禁止项写入根 `../AGENTS.md`。外部调用进一步补充取消传播、流式开始后禁止整体重试、幂等和观测字段。

## 3. 架构下：容量假设要变成演进触发器

课程先画 50 人部署，再预测瓶颈：真正压力不是普通 QPS，而是 3-30 秒模型调用和 SSE 长连接。它反对提前上多副本、MQ、独立向量库和微服务，并给出逐阶段扩容思路。数据设计强调领域分组、引用溯源、索引、唯一约束、游标分页和向量索引。

**融入设计**：Hify 一期用 Nginx + 单 Hify App + PostgreSQL/pgvector + 可选 Redis，避免课程示例中 MySQL 与 pgvector 双数据库并存。扩容只由连接数、队列等待、数据库规模、可用性和团队发布冲突等可观测条件触发。

## 4. 工程规范：短地图、详细制度、重复流程三层分离

课程把根级 CLAUDE.md 视为每轮加载的合作协议，建议包含项目上下文、架构、代码组织、部署/数据库和接口/行为指令；目录级规则叠加生效。详细 API/schema 放 docs/spec，反复出现的操作流程才沉淀为 Skill。规范应能追溯到架构决策或真实跑偏问题，并随项目渐进生长。

**融入设计**：Codex 项目使用等价的根 `../AGENTS.md`，只保留短地图和硬规则；详细内容拆入 `docs/`，关键选择写 ADR。当前不创建大量 Skills，等 CRUD、迁移、Provider 适配或模块交付流程真实重复后再提炼。

## 四讲合并后的判断

1. 产品裁剪、架构、部署、数据和 Agent 行为规范必须是一条因果链，不能独立成五份互相矛盾的文档。
2. AI 输出是候选方案，不是事实；需要用当前约束和代码证据判断。课程中的 K8s、双数据库、BIGINT/禁 NULL 等规则不应无条件照搬。
3. 对 Hify 而言，最该前置的不是微服务，而是 Query Loop 的终止、权限、预算、取消、事件 replay 和副作用幂等。
4. “为未来可拆”应通过模块接口、事件和数据 owner 实现，而不是今天提前支付分布式成本。

## 课程示例与本设计的差异

| 课程示例 | Hify 当前决策 | 原因 |
|---|---|---|
| MySQL + 独立 pgvector | PostgreSQL + pgvector | 少一个数据库，事务、备份和运维更简单 |
| 生产 Kubernetes | 先 Docker Compose | 20-50 人单实例不需要 K8s；保留触发条件 |
| Redis 保存会话上下文 | PostgreSQL 保存消息，Redis 仅加速/replay | 避免 Redis 成为不可恢复事实源 |
| 通用 60/120 秒超时 | connect/read/idle/overall 分层 | 流式连接持续时间不等于读空闲超时 |
| 未来跨模块接口可直接变 Feign | 先明确 application port 和 DTO | 本地接口与远程契约并不天然等价，仍需版本/错误/幂等设计 |
| 自增 BIGINT 主键、禁止 UUID | 对外 UUIDv7/ULID；内部实现不形成 API 契约 | 不暴露业务规模；时间有序 ID 缓解随机 UUID 的索引写放大 |
| 一律禁止 NULL，以 0/空串代替 | 必填字段 `NOT NULL`，未知/不适用保留 NULL | 避免哨兵值与真实业务值混淆，减少歧义分支 |
| Controller/Service/Mapper 三层 | api/application/domain/infrastructure 四层 | 分离用例/事务/取消编排与状态机/权限等领域规则 |

## 关键方法论速查

1. 先研究标杆全貌，再按自己的用户、团队和部署约束裁剪，不照抄功能列表。
2. 用三问裁剪：没有是否成立、做到什么程度够用、能否一句话说清。
3. 技术选型优先团队熟悉度、统一性和总维护成本，不追逐局部生态最优。
4. 单体部署不等于无模块边界；跨模块只走明确契约，依赖必须单向。
5. 外部调用同时考虑隔离、熔断、分层超时、分类重试和取消。
6. 先预测瓶颈并定义可观测触发器；触发前不提前支付分布式复杂度。
7. 数据模型先定领域关系、事实 owner 和关键约束，字段细节随实现迭代。
8. 根 AGENTS 只放短地图和硬规则，详细设计放 spec/ADR，重复流程再提炼 Skill。
9. 新规范必须能追溯到架构决策、缺陷或 Agent 的反复跑偏。
10. AI 给候选方案，人负责验证事实、识别约束、做取舍并留下理由。
